# Company Vercel production deployment

This repository prepares a production pipeline for the remote MCP boundary. No Vercel project, domain, secret, deployment or preview is created by this change. MyArchitectAI is on the restricted production list: obtain Justin's explicit approval for each merge or production promotion before using this pipeline.

## Project setup when the company creates it

1. Create an empty project in the **MyArchitectAI company Vercel team** for this repository; a Git connection is optional because the workflow identifies the existing project by ID. With the company scope selected, `vercel project add myarchitectai-mcp` creates the project through the [project CLI](https://vercel.com/docs/cli/project); project creation and the later approved deployment are separate steps. Set its root directory to the repository root, production branch to `main`, and Node.js version to **24.x**. Vercel detects the root `server.ts` shim, which imports the hosted implementation at `src/server.ts`; `src/index.ts` remains the stdio CLI entry. Do not select a static output directory or a prebuilt deployment path. The workflow sends source to Vercel for its remote build.
2. Keep automatic Git deployments disabled for **all** branches. The repository's `vercel.json` sets `git.deploymentEnabled` to `false`; if Git is connected, verify that project Git settings do not create separate deployments. The only configured deployment path is `.github/workflows/deploy-prod.yml` after a `main` push or a manual run against current `main`. No preview deployment is requested by this repository.
3. Assign `mcp.myarchitectai.com` as the production domain in Vercel and configure the company DNS for that domain. Confirm HTTPS reaches this project before interpreting a live verifier result.
4. Add these **GitHub Actions secrets** to `MyArchitectAI/myarchitectai-api-mcp`: `VERCEL_TOKEN` (a company team token permitted to deploy this project), `VERCEL_ORG_ID` (company team ID), and `VERCEL_PROJECT_ID` (this project's ID). The workflow fails before build or deployment if one is missing. It uses these values to select the existing project without `vercel link` or local `.vercel` files.
5. Configure only the approved **Production** runtime values in Vercel project settings. The hosted adapter requires `MCP_BILLING_MODE=api-balance`, `PORTAL_SUPABASE_URL`, `PORTAL_SUPABASE_SERVICE_ROLE_KEY`, `MCP_OAUTH_CLIENT_IDS`, `MCP_PORTAL_KEY_BINDINGS`, `AWS_REGION`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN`, and `MCP_HISTORY_KEY_SECRET`. `MCP_PORTAL_KEY_BINDINGS` is an operator-owned JSON subject-to-numeric-API-key-ID map, never an API key value; the adapter checks current ownership for each request. Optional settings are `AWS_SESSION_TOKEN`, `MCP_CANONICAL_RESOURCE` (defaults to `https://mcp.myarchitectai.com/mcp`), `MCP_ALLOWED_HOSTS`, `MCP_ALLOWED_ORIGINS`, and `OBS_HEALTH_TOKEN`. The issuer and JWKS derive from `PORTAL_SUPABASE_URL`. `MCP_DEPLOYMENT_REVISION` is supplied by the workflow to both build and runtime and must not be set by hand. Do not put runtime credentials in GitHub artifacts or pull Production environment files into CI.

`MCP_OAUTH_CLIENT_IDS`, `MCP_ALLOWED_HOSTS`, and `MCP_ALLOWED_ORIGINS` use JSON arrays; `MCP_PORTAL_KEY_BINDINGS` uses a JSON object keyed by exact lowercase user IDs; `MCP_HISTORY_KEY_SECRET` needs at least 32 random characters. `MCP_BILLING_MODE=api-balance` is an explicit product choice, not a deployment default. Do not enable it or add live customer bindings until Justin approves the billing source and the consent/account flow is tested. Missing required configuration fails closed; the pipeline then cannot claim a verified live boundary. The empty company project, domain, and CI IDs can be prepared while that decision remains open.

## Pipeline and evidence

The workflow installs locked dependencies, builds, typechecks, lints, runs unit and verifier tests, runs the synthetic remote HTTP smoke, and checks the live published API contract. The verifier fixture test also runs in ordinary PR CI as the named `deploy-contract` step. The workflow fetches `origin/main` immediately before deployment and rejects an old manual run or superseded push. It then runs pinned `vercel@61.0.0` as a **source** production deployment, passing the exact tested Git SHA as `MCP_DEPLOYMENT_REVISION`. The pin postdates Vercel's native `server.ts` support; the CLI version and source deployment mode are deliberate.

After Vercel accepts the deployment, `scripts/verify-deployment.mjs` probes the **canonical production domain**, not the generated deployment URL. It requires `/health` to report the exact tested SHA, protected-resource metadata to identify `https://mcp.myarchitectai.com/mcp` and an HTTPS authorization server, and an unauthenticated `POST /mcp` to return a 401 Bearer challenge pointing to the canonical metadata URL. The probe sends no bearer token and calls no paid tool. A failed probe fails the workflow even when Vercel accepted the deployment. The run summary records the source SHA, run URL, Vercel deployment URL when available, deploy outcome and live verification outcome; a successful upload is never reported as a verified live boundary.

This check proves only the deployed revision and public authentication boundary. It does **not** prove OAuth consent, authorization-server audience/refresh/revocation, customer account mapping, billing, or authenticated tool execution. Those integrations and a reviewer account need their own real end-to-end acceptance before the connector is described as usable. A fail-closed preparation service may satisfy the boundary check while refusing all customer tools.
