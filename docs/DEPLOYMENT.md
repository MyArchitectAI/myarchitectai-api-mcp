# Company Vercel production deployment

This repository prepares a production pipeline for the remote MCP boundary. The company Vercel project `myarchitectai-mcp` and domain already exist; reuse them. MyArchitectAI is on the restricted production list: obtain Justin's explicit approval for each merge or production promotion before using this pipeline.

## Production configuration

1. Use `myarchitectai-mcp` in the **MyArchitectAI company Vercel team**. Its root directory is the repository root, production branch is `main`, and Node.js version is **24.x**. A Git connection is optional because the workflow identifies the existing project by ID. The repository sets `framework: "node"` to select Vercel's native Node backend. `framework: null` selects Other and restricts function discovery to the `api` directory, so it cannot match this server's function configuration. Keep `outputDirectory: "."`: the native backend otherwise detects the CLI build's `dist` directory and selects its `index.js` stdio entry instead of the root `server.ts` shim. The explicit source-root setting keeps Vercel's hosted source bundle while `npm run build` still validates the compiled CLI. The shim imports the hosted implementation at `src/server.ts`; npm's `main`, `bin` and `start` remain the stdio CLI. The workflow sends source to Vercel for its remote build; do not select `dist` or a prebuilt deployment path.
2. Keep automatic Git deployments disabled for **all** branches. The repository's `vercel.json` sets `git.deploymentEnabled` to `false`; if Git is connected, verify that project Git settings do not create separate deployments. The only configured deployment path is `.github/workflows/deploy-prod.yml` after a `main` push that changes runtime source (`src/**`, `server.ts`), dependencies (`package.json`, `package-lock.json`) or production build/deployment inputs (`tsconfig.json`, `vercel.json`, `.vercelignore`, `.npmrc`). Documentation, tests and CI-only changes still run ordinary CI without requesting a production deployment. A manual run against current `main` remains available regardless of changed paths. No preview deployment is requested by this repository.
3. Assign `mcp.myarchitectai.com` as the production domain in Vercel and configure the company DNS for that domain. Confirm HTTPS reaches this project before interpreting a live verifier result.
4. Add these **GitHub Actions secrets** to `MyArchitectAI/myarchitectai-api-mcp`: `VERCEL_TOKEN` (a company team token permitted to deploy this project), `VERCEL_ORG_ID` (company team ID), and `VERCEL_PROJECT_ID` (this project's ID). The workflow fails before build or deployment if one is missing. It uses these values to select the existing project without `vercel link` or local `.vercel` files.
5. Deploy and verify the companion API Portal bridge before activating the MCP. Portal keeps its existing AWS and database credentials. In Portal Production configure `PORTAL_BASE_URL=https://portal.myarchitectai.com`, `MCP_CANONICAL_RESOURCE=https://mcp.myarchitectai.com/mcp` and `MCP_PORTAL_SIGNING_SECRET`. Use the Portal companion PR’s `docs/mcp-bridge.md` for setup and read-only verification. The bridge uses the signed-in user’s existing API account and newest enabled owned key; live consent still needs acceptance verification.
6. In **MCP Production**, configure `MCP_BILLING_MODE=api-balance`, `PORTAL_BASE_URL` (Portal origin and OAuth issuer) and the same `MCP_PORTAL_SIGNING_SECRET`. Optional settings are `MCP_CANONICAL_RESOURCE`, `MCP_ALLOWED_HOSTS`, `MCP_ALLOWED_ORIGINS`, and `OBS_HEALTH_TOKEN`. Store the shared signing credential as a sensitive server-only variable. `MCP_DEPLOYMENT_REVISION` remains workflow-supplied. Runtime secrets must not be pulled into CI or put in artifacts.
7. Remove obsolete `PORTAL_SUPABASE_URL`, `PORTAL_SUPABASE_SERVICE_ROLE_KEY`, `AWS_REGION`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `MCP_PORTAL_KEY_BINDINGS`, `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN` and `MCP_HISTORY_KEY_SECRET` from the **MCP** project. Keep Portal’s existing database and AWS credentials; retire obsolete MCP history and connector-binding settings without rotating Portal credentials. No new AWS identity, policy, API key or infrastructure is required for this integration.

`MCP_ALLOWED_HOSTS` and `MCP_ALLOWED_ORIGINS` use JSON arrays. Portal provides OAuth metadata, client registration, consent, S256 PKCE exchange, rotating refresh and revocation; hosted MCP has no static OAuth client list or JWKS setting. Clients approve API scopes, access tokens last at most fifteen minutes, and grants expire after thirty days. Portal checks the live grant and endpoint scope on every execution, so revocation blocks subsequent calls before token expiry. The Portal signing secret must have at least 32 random characters. API users/API-balance billing is the approved scope; subscription users are outside this change. Missing runtime configuration fails closed. The public process-health verifier alone does not establish that Portal delegation or user OAuth works.

## Companion release

Coordinate the reviewed Portal migration and application revision with the hosted MCP revision. Both services must agree on issuer, canonical resource, shared-secret reference and grant-bearing delegation. A mixed release fails closed. Use the private Portal checklist for identity-provider cutover and existing-session handling; do not infer those steps from a passing MCP deployment probe.

Before production promotion, verify browser consent and login return with an isolated reviewer account, approved scope subsets, refresh/downscoping and live revocation. The two-service synthetic harness must prove denied scopes and revoked grants cause no generation call. Production schema/configuration changes and paid acceptance calls need their own authorization. Reconnect existing clients through the Portal authorization server after the coordinated cutover.

## Pipeline and evidence

The workflow installs locked dependencies, builds, typechecks, lints, runs unit and verifier tests, runs the synthetic remote HTTP smoke, and checks the live published API contract. The verifier fixture test also runs in ordinary PR CI as the named `deploy-contract` step. The workflow fetches `origin/main` immediately before deployment and rejects an old manual run or superseded push. If a non-runtime push supersedes an in-flight runtime deployment, manually dispatch the workflow against current `main` to complete that release. It then runs pinned `vercel@61.0.0` as a **source** production deployment, passing the exact tested Git SHA as `MCP_DEPLOYMENT_REVISION`. The pin postdates Vercel's native `server.ts` support; the CLI version and source deployment mode are deliberate.

After Vercel accepts the deployment, `scripts/verify-deployment.mjs` probes the **canonical production domain**, not the generated deployment URL. It requires `/health` to report the exact tested SHA, protected-resource metadata to identify `https://mcp.myarchitectai.com/mcp` and an HTTPS authorization server, and an unauthenticated `POST /mcp` to return a 401 Bearer challenge pointing to the canonical metadata URL. The probe sends no bearer token and calls no paid tool. A failed probe fails the workflow even when Vercel accepted the deployment. The run summary records the source SHA, run URL, Vercel deployment URL when available, deploy outcome and live verification outcome; a successful upload is never reported as a verified live boundary.

This check proves only the deployed revision and public authentication boundary. It does **not** prove OAuth consent, authorization-server audience/refresh/revocation, customer account mapping, billing, or authenticated tool execution. Those integrations and a reviewer account need their own real end-to-end acceptance before the connector is described as usable. A fail-closed preparation service may satisfy the boundary check while refusing all customer tools.
